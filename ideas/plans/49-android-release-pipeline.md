## MVP 범위
- GitHub Actions 재사용 워크플로: 빌드 → AAB 서명 → Play 업로드 → 트랙(내부·비공개·프로덕션) 지정 → 출시 노트 → 검토 제출
- 출시 전 가드:
  - 트랙별 광고 ID 규칙 (테스트 트랙 = 구글 테스트 ID, 프로덕션 = 실제 ID) 불일치 시 실패
  - versionCode가 Play에 이미 있는 값보다 큰지 확인
  - 패키지명·서명 키 지문이 기록과 같은지 확인
  - 권한·타깃 SDK 정책 경고
- 출시 노트: 커밋 메시지·변경 기록에서 한국어 출시 노트 초안 생성
- 비공개 테스트 추적: 테스터 수·참여 기간(14일 요건) 현황 리포트
- 앱 내 업데이트: Play In-App Updates 공통 모듈 (사용자 선호: 앱 안에서 업데이트)

## 기술 구조
- Google Play Developer API (edits: 업로드·트랙·출시 노트·커밋), 서비스 계정 키는 GitHub 비밀 저장소
- 검증된 공개 도구(fastlane supply 또는 Gradle Play Publisher)를 업로드 엔진으로 사용하고, 가드·노트·리포트를 그 위에 구현
- 앱별 설정: `release.yml`(패키지명, 트랙 정책, 광고 ID 파일 경로, 서명 지문)
- 알림: 텔레그램 + 웹 푸시(아래 대시보드), 31번 kit 알림 부품은 가져다 쓰기만 함

## 배포 형태 (2026-10-23 검토 · 권장안)
**결론: 핵심은 GitHub Actions(서버에서 자동 실행) + 화면은 웹(설치형 웹앱, PWA). 안드로이드 APK는 지금 만들지 않음.**

| 기준 | 웹(PWA) | 안드로이드 앱(APK) |
|---|---|---|
| 실제 작업이 일어나는 곳 | 빌드·업로드·검사는 어차피 GitHub Actions에서 실행 → 화면은 상태 보기·승인만 하면 됨 | 동일 (앱도 결국 GitHub를 호출) |
| 폰 중심 사용 | 홈 화면에 설치, 웹 푸시 알림, 승인 버튼 → 폰에서 충분 | 가장 자연스러움 |
| PC 연동 | 같은 주소로 PC에서 상세 로그·출시 노트 편집 | PC 화면 따로 필요 |
| 비밀키 보관 | Play 서비스 계정 키는 GitHub 비밀 저장소에만, 웹은 GitHub 로그인(OAuth)만 | 폰에 GitHub 토큰 저장 필요 → 분실 시 위험 |
| 자체 출시 부담 | 없음 (배포 = 정적 사이트 갱신) | "출시 도구"를 또 플레이스토어에 출시·심사 받아야 함, 업데이트마다 같은 수고 |
| 나중에 판매(다른 개발자용) | 웹 SaaS로 그대로 확장 | 개발자는 주로 PC에서 작업 → 수요 적음 |
| 개발 비용 | 화면 몇 개 (상태·승인·테스터 현황·설정) | 앱 + 서명·스토어 등록·심사 |

- **1단계(지금)**: GitHub Actions 재사용 워크플로 + 텔레그램 알림 → 화면 없이도 출시 자동화 완성
- **2단계**: 웹 대시보드(PWA) — 앱별 최근 출시·트랙·버전, 검사 결과, 프로덕션 승인 버튼(GitHub 환경 승인 호출), 비공개 테스트 14일 진행 현황, 출시 노트 편집. GitHub Pages/Cloudflare Pages에 정적 배포, 로그인은 GitHub OAuth, 본인 계정만 허용
- **3단계(선택)**: 폰 위젯·더 강한 알림이 꼭 필요해지면 PWA를 감싼 얇은 안드로이드 앱(TWA)을 이 파이프라인 자신으로 출시 — 새로 짜는 게 아니라 같은 웹을 포장만 함
- 판매 검토 시: 웹 SaaS(다른 개발자의 GitHub 연결)로 확장, 결제는 39번 엔진
